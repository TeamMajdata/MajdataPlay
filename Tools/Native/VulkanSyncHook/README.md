# Vulkan index/vertex visibility hook

Windows x64 native **Unity preload plug-in**. It repairs one specific Vulkan synchronization defect that the engine's own command stream contains.

> **Status: diagnostic, not a shipped fix.** The repair is verified to remove the corresponding Khronos synchronization-validation diagnostics, but its effect on the nvlddmkm Event ID 153 device loss is **not** established. See *Evidence status* below before enabling it in a release build.

## The defect

The engine records `vkCmdCopyBuffer` into a small index or vertex buffer and then draws from that buffer with `vkCmdDrawIndexed` in the same submission, without any availability/visibility dependency. Vulkan requires one: queue submission order alone does not make a buffer write visible to a later read. Khronos synchronization validation reports `SYNC-HAZARD-READ-AFTER-WRITE` for a 936-byte and a 12-byte index buffer, and it reproduces on a pristine player in the `Init → Title` scene before any chart content exists, so the defect belongs to the engine path rather than to game code.

Because the command stream is generated by the engine, there is no C#-level seam to fix it. This plug-in is the only in-process repair available.

## What it does

`UnityPluginLoad` registers one `AddInterceptInitialization` callback at priority `0x40000000` and wraps `vkGetInstanceProcAddr`/`vkGetDeviceProcAddr`, so the wrappers are installed before the instance and swapchain exist. Self-queries keep returning the wrapper, which prevents a lower resolver from being cached and silently bypassing the interceptor.

`vkCmdCopyBuffer` is wrapped: the original call is forwarded first with unchanged arguments, and then — only when the destination buffer was created with `INDEX_BUFFER` and/or `VERTEX_BUFFER` usage — one `vkCmdPipelineBarrier` is appended to the same command buffer.

| Field | Value |
| --- | --- |
| `srcStageMask` | `VK_PIPELINE_STAGE_TRANSFER_BIT` |
| `dstStageMask` | `VK_PIPELINE_STAGE_VERTEX_INPUT_BIT` |
| `srcAccessMask` | `VK_ACCESS_TRANSFER_WRITE_BIT` |
| `dstAccessMask` | `VK_ACCESS_INDEX_READ_BIT \| VK_ACCESS_VERTEX_ATTRIBUTE_READ_BIT` |
| `buffer` / `offset` / `size` | destination buffer / `0` / `VK_WHOLE_SIZE` |
| queue families | `VK_QUEUE_FAMILY_IGNORED` |

Buffer usage is tracked by wrapping `vkCreateBuffer`/`vkDestroyBuffer` behind a mutex. Driver calls always run outside the lock and are forwarded before any bookkeeping. `vkCmdPipelineBarrier` is resolved through the next-link chain, so validation layers and the driver still observe the injected command as an ordinary recorded command.

The narrow form deliberately waits only for `VERTEX_INPUT`. It does not stall the whole queue the way a `ALL_COMMANDS` barrier would, which is what makes it usable as a targeted repair rather than a blunt serialization.

## Modes

`MAJ_VULKAN_SYNC_HOOK` is read once during preload:

| Value | Behaviour |
| --- | --- |
| unset | **narrow** repair (default) |
| `0` | disabled; nothing is registered and no interceptor is installed |
| `2` | broad form: every copy gets `TRANSFER_WRITE → MEMORY_READ` with `ALL_COMMANDS` |

One line is appended to `vulkan-sync-hook.log` beside the player executable at load and once interception is registered, so activation is verifiable without a debugger. A diagnostic set of `bb_*` counters is exported for harnesses; they are never read on the hot path.

## What it does not fix

Image-side hazards remain untouched: the swapchain clear → render-pass implicit layout transition (`WRITE_AFTER_WRITE`) and the acquire → `TRANSFER` layout transition (`WRITE_AFTER_READ`). The hook does not change engine rendering, resources, queues or the swapchain, and it does not create any Vulkan object.

## Deployment

Place the built `MajdataPlayVulkanSyncHook.dll` in `MajdataPlay_Data/Plugins/x86_64/`. Unity preloads plug-ins from that folder, so `UnityPluginLoad` runs before the graphics device is created. An existing project may already occupy a preload slot with a different filename; in that case the file can be renamed to that slot's name, but the original plug-in then stops running, so keep a backup.

Known interaction: `FFmpegUnityBridge` also intercepts initialization, at maximum priority. Both must be present and correct; verify the video path still reports native GPU frames after enabling this hook.

## Evidence status

- Verified with Khronos core + synchronization validation on a pristine player: with the hook installed, the 936/12-byte `READ_AFTER_WRITE` diagnostics disappear and only the image-side hazards remain. The activation log confirms the interception was registered.
- **Not** proven to reduce device loss: a 12-versus-12 chart soak gave 0/12 with the narrow repair against 2/12 without, which is not statistically significant (Fisher one-sided p ≈ 0.24). A separate 3-run soak on a pristine build with the hook completed without driver events, which is likewise too small to conclude anything.
- Platform coverage is Windows x64 only. Linux, macOS, Android and IL2CPP builds are unverified.

## Build

```powershell
./build.ps1
```

Uses the local Visual Studio 2022 Community x64 MSVC toolchain and CMake with the repository's Unity headers and pinned Vulkan-Headers copy; no download and no Editor. Outputs `.build/Release/MajdataPlayVulkanSyncHook.dll` and hashes in `.build/build-manifest.json`. `MajdataPlayVulkanSyncHookTests` runs against fake entry points and covers mode selection, copy-before-barrier ordering, narrow field values, skipping non-index/vertex buffers, usage lifetime after destroy, and shutdown rejection.
